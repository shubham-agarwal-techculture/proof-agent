# ProofAgent — Phase 9 Walking Skeleton

A minimal, **building and passing** Lean 4 project that demonstrates the design's **trusted core**: a
verifier gate that rejects cheating proofs and admits only honest, on-statement, allow-listed-axiom
results, wrapped in a propose → verify → record loop with content-addressed memory.

> **Build status: VERIFIED.** Built and run on Windows with Lean **4.35.0**
> (`leanprover/lean4:v4.35.0`, confirmed as a real release). `lake build` succeeds and all four test
> suites exit 0 — cheats rejected, only verified results persisted, diagnostics and goal states read
> back. See `../docs/phase-9-walking-skeleton.md` for the exact recorded results.

## Layout

```
skeleton/
├─ lean-toolchain              # pinned Lean version: leanprover/lean4:v4.35.0
├─ lakefile.toml               # NO external deps by design (trusted base stays minimal)
├─ lake-manifest.json          # generated by lake
├─ ProofAgent.lean             # library root (imports the modules)
├─ ProofAgent/
│  ├─ Spec.lean                # ProblemSpec, Claim  (untrusted artifacts)
│  ├─ VerifierGate.lean        # the trusted gate: banned tokens, statement match, axiom audit
│  ├─ Memory.lean              # append-only, content-addressed JSONL store + dedup insert
│  ├─ Orchestrator.lean        # propose → verify → record; verified-only memory
│  └─ Tools/
│     ├─ LeanCheck.lean        # spawns `lean --json`, parses diagnostics → CheckResult
│     ├─ GoalState.lean        # probes a statement, parses the unsolved-goals diagnostic → goals
│     └─ CheckServer.lean      # stdin/stdout JSON request loop (`lake exe checkServer`)
└─ tests/
   ├─ adversarial.lean         # cheat proofs that MUST be rejected + one honest proof that passes
   ├─ memory.lean              # store ops, dedup, and gate→persist end-to-end
   ├─ leancheck.lean           # good / bad / unknown-tactic / sorry compile outcomes
   └─ goals.lean               # initial goal read-back (incl. a false and an ill-typed statement)
```

## What it demonstrates

| Concept (design ref) | In this skeleton |
|---|---|
| Invariant #1 (trusted core) | `VerifierGate.gate` is total & deterministic; agents only *propose* |
| F1 kernel bypass | rejects `sorry`, `native_decide`, `unsafe`, `implemented_by`, `partial`, `skipKernelTC` |
| F2 statement drift | `statementMismatch` when `provedHash ≠ spec.specHash` |
| F3 axiom inflation | `forbiddenAxiom` for anything outside `{propext, Classical.choice, Quot.sound}` |
| A1 compiled ≠ verified | only `gate = .verified` writes a `verified` memory entry |
| F7 memory poisoning | rejections never enter verified memory (`Orchestrator.step`, `verifyAndRecord`) |
| Invariant #3 provenance | `MemEntry` carries hash, producer, status; persisted as JSONL |
| Invariant #3 append-only | `Memory.insert` only ever appends; entries are never mutated |
| Phase-5 dedup lever | `Memory.insert` dedups by content key (second identical insert is a no-op) |
| §5.3 Lean tool | `LeanCheck.checkSource` runs the pinned `lean --json` and parses diagnostics |
| §5.3 goal read-back | `GoalState.goalState` probes a statement (`example : … := by skip`) and reads back its initial goal(s) |
| A1 compiled ≠ verified | the check tool accepts a `sorry` proof (warning only) — the gate is what rejects it |

## How to run

```powershell
# 1. Install the Lean toolchain manager (once)
#    https://leanprover-community.github.io/get_started.html  (installer: elan)

# 2. From the skeleton folder
cd skeleton

# 3. Build the trusted core (seconds — no Mathlib needed)
lake build

# 4. Run the adversarial tests
lake env lean tests/adversarial.lean

# 5. Run the memory-store tests
lake env lean tests/memory.lean

# 6. Run the Lean-check-tool tests
lake env lean tests/leancheck.lean

# 7. Run the goal-state tests
lake env lean tests/goals.lean

# 8. Exercise the tool server (one JSON request per line on stdin)
'{"id":"r1","op":"check","source":"theorem a : 1 + 1 = 2 := rfl"}' | lake exe checkServer
'{"id":"r2","op":"goals","statement":"1 + 1 = 2"}' | lake exe checkServer
```

## Notes & deliberate choices

- **No Mathlib dependency.** The trusted gate uses only Lean core, so the trusted base stays small
  and auditable (invariant #1) and the build takes seconds. Add Mathlib in `lakefile.toml` when the
  *pipeline* (not the gate) needs it — the commented `[[require]]` block shows how.
- **Textual scan vs. elaborated `Expr`.** `scanBanned` is a stand-in for the real design's inspection
  of the *elaborated* expression plus `#print axioms` plus an **independent re-check**
  (nanoda/con-leche/lean4lean-class), which is what makes a result `verified` (Phase 1 A1).
- **Why `#eval`, not `by decide`, for the gate verdicts.** `String.splitOn` is `@[extern]` and does
  not reduce in the kernel; the machine-checked `example`s cover the axiom allow-list logic, which is
  pure `String` equality. The elaborated-`Expr` gate is kernel-reducible and can be proved about.

- **Non-cryptographic content key.** `Memory.contentHash` is FNV-1a, used only to give entries a
  stable key for dedup in the skeleton; the production system hashes canonical artifact bytes with
  SHA-256. The store is append-only and `insert` is a no-op when the content key already exists.

- **The check tool spawns `lean` from `PATH`.** Run it under `lake env ...` (or with elan's shims on
  `PATH`) so the pinned `lean` is found. It reports *compilation*, not verification: a `sorry` proof
  compiles and is accepted here, and is rejected later by the gate — the A1 division of labour.
- **Goal read-back is one-shot, not interactive.** `GoalState.goalState` reads the *initial* goal of a
  statement by compiling `example : <statement> := by skip` and parsing the `unsolved goals` diagnostic.
  It does **not** step a proof forwards a tactic at a time — that needs a live session (the
  `leanprover-community/repl` package or the Lean LSP server), which is deferred (see phase-9 §6). The
  win is that the prover loop can now read goals with the same zero-dependency `lean --json` plumbing.

## Scope & honesty

This is a **skeleton**, not the system. It proves the *policy* of the trusted boundary works, and it
ships three real tools (a Lean check tool, a goal-state reader, and an append-only JSONL store); it does
not yet implement elaboration-based statement matching, `#print axioms` wiring, *interactive* goal
stepping, or the independent re-checker. To make it real, follow `../docs/phase-9-walking-skeleton.md` §6.
